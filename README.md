# 📧 LARK-MAIL 邮件监控推送

[![Python](https://img.shields.io/badge/Python-3.7+-3776AB?logo=python&logoColor=white)](https://www.python.org/)
[![Docker](https://img.shields.io/badge/Docker%20Compose-✓-2496ED?logo=docker&logoColor=white)](docker-compose.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)

> 监控邮箱收件箱,每当收到新邮件时,自动通过飞书自定义机器人推送通知到飞书群。
> 基于 IMAP 协议轮询,一条命令 Docker 部署,开箱即用,支持**单账户 / 多账户**两种模式。

## ✨ 功能特性

- 📬 **IMAP 轮询监控**:定时检查邮箱新邮件(默认每 60 秒一次)
- 🧭 **状态与已读解耦**:用本地 UID 水位线记录"推送过没有",**与已读/未读状态完全无关**。邮件在两次轮询之间被人读过也照样能推到
- 📖 **对邮件完全只读**:默认模式下脚本**不改已读、不改已回复、不加任何关键字**,连 `STORE` 命令都不发。多人共用一个邮箱,同事察觉不到任何异常
- 🔒 **本地状态双保险**:状态写在 `data/uid_state.json`,每次写入自动保留一份 `.bak`;主文件损坏/被误删时自动从备份恢复
- ⚙️ **状态记录方式可选**:默认 `watermark`(纯本地,完全不碰邮件);另有 `keyword` / `answered` 两种会改动邮件的模式,只在明确需要时才用
- 📚 **多账户并行监控**:一个容器同时监控多个邮箱,每个账户独立线程运行,互不影响
- 📨 **飞书卡片推送**:以交互卡片形式推送通知,包含发件人、主题、时间、正文预览(前 500 字符)、附件名
- 🛡️ **防封号处理**:模拟 Outlook 客户端发送 IMAP `ID` 命令,规避网易等邮箱的 "Unsafe Login" 拦截
- ⏱️ **防限流机制**:每封邮件之间可配置延时(带随机抖动),避免触发飞书 Webhook 频率限制
- 🔕 **旧邮件过滤**:冷启动时用 `SINCE` 条件限定最近 `BLOCK_BEFORE` 秒内,远古积压邮件不会被补推(省流量、避免旧邮件 fetch 失败报错)
- 🚫 **关键词与发件人屏蔽**:支持按账户配置屏蔽词(命中主题或正文)与屏蔽发件人(命中 From 头),命中的邮件自动跳过,不推送;中英文逗号分隔;匹配前两侧统一做 **NFKC 归一化 + casefold**,**忽略大小写、全角/半角、空白与零宽字符差异**(垃圾邮件用空格/零宽字符拆字规避屏蔽也无效);重复词条自动去重
- 🧠 **屏蔽邮件本地记忆**:命中的邮件**保持未读**(收件箱仍可见),但本地记录后不再重复拉取、不占每轮抓取额度,也不会每轮刷一遍"命中屏蔽"日志
- ⚖️ **批量控制**:单次最多处理 N 封(默认 50 封),防止积压时一次性推送过多
- 💬 **降级容错**:卡片消息发送失败时自动回退为纯文本消息重试
- ✅ **推送完不动邮件**:拉取用 `BODY.PEEK[]`(不会隐式标已读);推送成功后**既不标已读、也不标已回复、不加任何关键字**,只在本地记一笔
- 🔁 **失败重试有上限**:推送失败的邮件保持未标记自动重试,超过 `MAX_RETRIES` 次(默认 3)后标记放弃,避免反复重试刷屏
- 🛡️ **重复推送去重**:以邮件 `Message-ID`(缺失时用 发件人+主题+时间 指纹)做进程内跨账户去重,同一封邮件只推送一次;标记失败、同邮箱配置多个账户等场景不再重复;去重命中时自动补标记。卡片响应超时视作已发送,不回退纯文本,避免同一条消息双发
- 🔌 **连接复用**:登录后连接持续复用,每 `RECONNECT_INTERVAL`(默认 10 分钟)才重连一次,大幅降低被邮箱服务器风控的概率;连接异常自动带退避重连(10 秒起,60 秒封顶)
- 🔄 **失败自愈**:主循环异常时自动捕获,持续运行不退出

## 🔧 工作原理

```
┌────────────┐   IMAP/SSL(993)   ┌────────────┐   HTTPS POST   ┌──────────────┐
│  邮箱服务器 │ ◄──────────────► │ lark-mail  │ ─────────────► │  飞书群机器人  │
│ (如163邮箱) │  标记+增量拉取     │   脚本      │  卡片消息      │  (Webhook)   │
└────────────┘                   └────────────┘                └──────────────┘
```

每次轮询执行以下流程:

1. 建立 IMAP 连接并登录(发送 `ID` 命令模拟 Outlook 客户端)——连接**复用**,不每轮重建
2. **按 UID 水位线拉取**:只拉 UID 大于上次处理位置的邮件,**完全不看 `\Seen` 状态**——这是"邮件在两次轮询之间被人打开就漏推"的根治办法。默认 `PUSH_MODE=watermark`,状态只在本地,脚本对邮件**只读**
   - 正常轮询走 UID 增量;水位线缺失时按冷启动处理(建立基线,历史邮件不补推)
3. 使用 `BODY.PEEK[]` 按数量限制拉取前 N 封(不会隐式标记已读)
4. 解析邮件:解码 MIME 头(主题/发件人)、提取正文(优先纯文本,回退 HTML 并去除标签)、提取附件名、解析日期(转换为北京时间)
5. 双重过滤:时间窗外的旧邮件跳过;命中 `blocked_keywords` 屏蔽词(主题/正文)或 `blocked_senders` 屏蔽发件人(From 头)的直接跳过——被过滤的邮件**保持未读**,且本地记忆后**下轮起在拉取阶段直接跳过**(不重复下载、不占抓取额度);命中日志会标注命中的规则与位置(主题/正文)
6. 推送:调用飞书 Webhook 发送卡片消息(含附件信息),失败则回退纯文本
7. **推送成功**后只在本地记一笔水位线,**邮件本身什么都不改** —— 不标已读、不标已回复、不加关键字。推送失败则不推进水位线,下轮自动重试,超过 `MAX_RETRIES` 次后标记放弃

> 用人话说:脚本跑完,你在邮箱里看到的、同事在邮箱里看到的,**都和没装这个脚本时一模一样**。
8. 每封邮件之间休眠 `BATCH_DELAY` 秒(带随机抖动),防止限流
9. 休眠 `POLL_INTERVAL` 秒后进入下一轮(连接保持复用,每 `RECONNECT_INTERVAL` 秒强制重连一次;连接异常时短退避后立即重试)

> 水位线只推进到**本轮真正拉取成功**的最大 UID。被 `MAX_EMAILS_PER_RUN` 截断的、拉取失败的邮件 UID 仍在水位线之上,下轮自动补上,不会因为额度限制漏水。

> 多账户模式下,每个账户**独立线程**并行执行上述流程,各自拥有独立的轮询间隔、屏蔽词与 Webhook。

## 🚀 快速开始

### 方式一:Docker Compose 部署(推荐)

1. **准备邮箱授权码**

   以 163 邮箱为例:登录网页版邮箱 → 设置 → POP3/SMTP/IMAP → 开启 IMAP 服务,获取**授权码**。注意:授权码不是邮箱登录密码。

2. **创建飞书机器人 Webhook**

   在飞书群 → 设置 → 群机器人 → 添加「自定义机器人」,复制 Webhook 地址。

3. **配置环境变量**

   ```bash
   cp .env.example .env
   ```

   编辑 `.env`,填入你的邮箱与飞书配置。

   > `.env` 已被 .gitignore 忽略,不会提交到仓库,请放心填写真实配置。
   > 配置方式有**单账户**和**多账户**两种,任选其一(详见下文「环境变量」章节)。
   > `docker-compose.yml` 已通过 `${VAR:-默认值}` 语法自动读取 `.env` 中的变量,
   > **日常只需改 `.env`,无需改动 yml 文件**。

4. **启动服务**

   ```bash
   docker compose up -d --build
   ```

   > 首次启动需要 `--build`(依赖预装进镜像,约 30 秒)。之后改配置只需
   > `docker compose restart`,改脚本也只需 restart(**代码是单独挂载的,不用 rebuild**)。

5. **查看日志**

   ```bash
   docker logs -f lark-mail
   ```

   启动日志里会有这么几行,用来确认状态文件挂载正常:

   ```
   📂 状态文件: /data/uid_state.json
   💾 已恢复 1 个邮箱文件夹的水位线 —— 重启后继续增量拉取
   [xxx@163.com] 📌 状态记录方式: 本地 UID 水位线(完全不碰邮件: 不改已读、不改已回复、不加关键字)
   ```

   **最后一行很重要** —— 确认显示的是"完全不碰邮件",说明脚本对邮箱是纯只读的。

   如果看到 `🆕 状态文件不存在` 或「状态文件目录不可写」告警,说明 `./data` 没挂上。
   这时脚本仍能正常推送,但**每次重启都会丢掉进度**,并跳过停机期间的历史邮件
   (见 FAQ 2.8),所以务必修好挂载。

## ⚙️ 环境变量

> **变量从哪来?** Docker 部署时,`docker-compose.yml` 通过 `${VAR:-默认值}` 语法自动读取同目录 `.env` 文件:
> `.env` 中已设置 → 使用 `.env` 的值;未设置或留空 → 使用表中的默认值。**只需编辑 `.env`,无需修改 yml。**

### 单账户模式变量

| 变量名 | 必填 | 默认值 | 说明 |
|--------|------|--------|------|
| `IMAP_SERVER` | 是 | `imap.163.com` | IMAP 服务器地址 |
| `IMAP_PORT` | 否 | `993` | IMAP SSL 端口 |
| `IMAP_USER` | 是* | - | 邮箱账号 |
| `IMAP_PASS` | 是* | - | **授权码**,不是邮箱登录密码 |
| `MAILBOX` | 否 | `INBOX` | 监听的邮箱文件夹 |
| `FEISHU_WEBHOOKS` | 是* | - | 飞书自定义机器人 Webhook 地址 |
| `BLOCKED_KEYWORDS` | 否 | 空 | 屏蔽词,中英文逗号 `,`/`，` 分隔均可;匹配主题/正文;忽略大小写/全半角/空白/零宽字符差异;重复词条自动去重 |
| `BLOCKED_SENDERS` | 否 | 空 | 屏蔽发件人,中英文逗号分隔;匹配 From 头(姓名/邮箱地址),同样忽略大小写/全半角/空白差异;子串匹配,建议写完整邮箱或 `@域名` 以免误伤 |
| `POLL_INTERVAL` | 否 | `60` | 轮询间隔(秒) |
| `BLOCK_BEFORE` | 否 | `86400` | 跳过多少秒之前的邮件(默认 24 小时) |
| `MAX_EMAILS_PER_RUN` | 否 | `50` | 每次轮询最多处理的邮件数 |
| `MAX_RETRIES` | 否 | `3` | 推送失败最大重试次数,超限后标记放弃(避免反复重试) |
| `RECONNECT_INTERVAL` | 否 | `600` | 连接复用下强制重连间隔(秒),默认 10 分钟重连一次,降低被邮箱风控概率 |
| `BATCH_DELAY` | 否 | `2.0` | 每封邮件之间的延时(秒),防止飞书限流 |
| `PUSH_MODE` | 否 | **`watermark`** | "已推送"状态的记录方式。**默认 `watermark` = 纯本地水位线,完全不碰邮件**。另有 `keyword` / `answered` 两种会改动邮件的模式,一般不要用。详见 [FAQ 2.6](#26-多个同事共用同一个邮箱会不会互相干扰) |
| `MARK_SEEN` | 否 | **`false`** | 推送成功后是否标为已读。**默认关闭**——共用邮箱下脚本不会改动邮件可见状态。想让脚本顺手标已读才设 `true` |
| `UID_STATE_FILE` | 否 | `./uid_state.json`(容器内为 `/data/uid_state.json`) | UID 水位线文件路径。默认模式下这是**唯一的状态来源**,必须放在持久化目录;写入时会自动保留 `.bak` 备份 |
| `DEBUG` | 否 | `false` | 设为 `true` 开启调试模式,输出 IMAP 交互详情与每轮检查日志(默认静默,只有新邮件/异常/重连才打日志) |

### 多账户模式变量(推荐)

| 变量名 | 必填 | 说明 |
|--------|------|------|
| `MAIL_ACCOUNTS_JSON` | 是* | 多账户 JSON 数组配置,设置后**优先**使用,单账户变量被忽略 |

> `*` 表示多账户模式(`MAIL_ACCOUNTS_JSON`)与单账户变量(`IMAP_USER` / `IMAP_PASS` / `FEISHU_WEBHOOKS`)二选一。

**JSON 格式说明:**

```json
[
  {
    "imap_user": "user1@163.com",               // 邮箱账号(必填)
    "imap_pass": "授权码1",                      // 授权码,不是登录密码(必填)
    "feishu_webhook": "https://open.feishu.cn/open-apis/bot/v2/hook/xxx",  // 飞书 Webhook(必填)
    "blocked_keywords": "广告,推广",             // 屏蔽词,中英文逗号分隔均可(可选)
    "blocked_senders": "APS,spam@x.com"         // 屏蔽发件人,建议完整邮箱或@域名(可选)
  },
  {
    "imap_user": "user2@qq.com",
    "imap_pass": "授权码2",
    "feishu_webhook": "https://open.feishu.cn/open-apis/bot/v2/hook/yyy",
    "blocked_keywords": ""
  }
]
```

**实际填写时(`.env` 或 docker-compose.yml 中)必须写成一行:**

```bash
MAIL_ACCOUNTS_JSON=[{"imap_user":"user1@163.com","imap_pass":"授权码1","feishu_webhook":"https://open.feishu.cn/open-apis/bot/v2/hook/xxx","blocked_keywords":"广告,推广"},{"imap_user":"user2@qq.com","imap_pass":"授权码2","feishu_webhook":"https://open.feishu.cn/open-apis/bot/v2/hook/yyy","blocked_keywords":""}]
```

> ⚠️ **多账户 JSON 不能换行!**
>
> - 必须写成**一整行**,即使只有一个账户也不例外
> - `.env` 或 docker-compose.yml 中换行,会把值拆成多行,脚本 `json.loads` 解析失败,服务直接报错无法启动
> - 账户之间用 `,` 分隔,整个数组用 `[` `]` 包裹,键名和值都要用**双引号**

## ❓ 常见问题

### 1. 登录报错 `Unsafe Login` / `LOGIN Login error` / 登录失败

- 确认 `IMAP_PASS` / `imap_pass` 填的是**授权码**而非登录密码
- 163/QQ 等邮箱需要在网页端开启 IMAP 服务
- 脚本已内置 `ID` 命令模拟 Outlook 客户端,若仍有问题可在 `DEBUG=true` 下查看详细日志
- 若 `LOGIN Login error` 表现为**时好时坏**(有时正常推送、有时连不上):多为邮箱服务器对高频重连的间歇风控。新版已改为**连接复用**(每 `RECONNECT_INTERVAL` 才重连一次)+ **失败退避**(10 秒起、60 秒封顶自动重试),升级代码并重启容器后通常自动缓解
- 确认授权码无误且连接稳定后仍持续失败,可尝试用浏览器登录一次网页版邮箱"激活"账号

### 2. 收不到飞书通知

- 检查 Webhook 地址是否正确(注意脚本读取的环境变量名为 `FEISHU_WEBHOOKS`,带 S)
- 确认飞书机器人未被移出群聊、Webhook 未被关闭
- 查看容器日志 `docker logs -f lark-mail`,确认是"没有新邮件"还是推送失败
- 检查是否被 `blocked_keywords` 屏蔽词误过滤(命中日志会显示命中的规则与位置;注意**子串匹配**——屏蔽词过短可能误伤,如 `aps` 也会命中 `maps`)

### 2.5 配置了屏蔽词/屏蔽发件人却没生效?

- **屏蔽词只匹配主题和正文**——要屏蔽某个发件人(如 "APS")请用 `blocked_senders` / `BLOCKED_SENDERS`,它匹配邮件 From 头(姓名和邮箱地址都会检查);屏蔽词为**子串匹配**,显示名含该子串即命中(如屏蔽 `金菊` 可命中 `jinjv金菊 <jinjv@example.com>`),但**纯拼音形态**(如 `jinjvjinju`)不会命中,这种情况请改用完整邮箱地址
- **分隔符**:必须用逗号分隔,中英文逗号 `,`/`，` 均可;词条首尾的空白(含换行/全角空格)会自动清理,纯空白条目与重复词条(含大小写/全半角变体)自动忽略
- **匹配规则**:屏蔽词与邮件内容两侧都做 NFKC 归一化(全角→半角)+ casefold(大小写折叠)+ 去空白/零宽字符后做子串匹配——垃圾邮件用 `免 费` 空格拆字、`免\u200b费` 零宽字符拆字等规避手段**均无效**;`no reply` 也能命中 `noreply`(有意拓宽,防拆字)
- 查看启动日志 `屏蔽词(N 条): ...` / `屏蔽发件人(N 条): ...` 两行,确认条数与内容(已去重,显示原始写法)
- 命中时日志会打印命中的规则与位置,如 `🚫 命中屏蔽词[正文] 规则: 中奖 | 保持未读,后续轮次不再处理 | ...`,便于排查哪条规则误伤

### 2.6 多个同事共用同一个邮箱,会不会互相干扰?

**默认不会。** 这一点在设计时专门处理过。

脚本必须记住"哪些邮件已经推送过"。这个记忆**默认全放在本地**,一个字节都不往邮件里写。

| `PUSH_MODE` | 状态存在哪 | 会改动邮件吗 | 同事能看到变化吗 |
|---|---|---|---|
| **`watermark`(默认)** | 本地 `data/uid_state.json` | **不会**,连 `STORE` 命令都不发 | **完全看不到** |
| `keyword` | 服务器(自定义关键字) | 会,加一个 `$LarkMailPushed` | 多数客户端不显示,但确实改了邮件 |
| `answered` | 服务器(`\Answered` 位) | 会 | ❌ Outlook/Foxmail 显示"已回复",共用邮箱禁用 |

默认配置:

```yaml
environment:
  - PUSH_MODE=watermark   # 默认:状态只在本地,完全不碰邮件
  - MARK_SEEN=false       # 默认:推送完不标已读
```

**这就是默认值,不用写。** 脚本对邮箱的所有操作只有 `SELECT` / `SEARCH` / `FETCH (BODY.PEEK[])` 三种,全是只读的 —— 不改已读、不改已回复、不加任何标记。同事那边看到的一切都和以前一样。

代价要说清楚:**状态只在本地**,所以 `./data` 必须挂载好:

```yaml
volumes:
  - ./data:/data
```

文件丢了会怎样?不会重复轰炸,但**会跳过停机期间的历史邮件**(冷启动时按"不补推历史"处理,避免一上来推几十条)。这是"绝对不碰邮件"必然要付的代价。

为了把这个风险降到最低,状态文件做了两重保护:

- 写入用"临时文件 + 原子替换",进程被杀不会留下半个 JSON
- 每次写入前保留一份 `uid_state.json.bak`,主文件损坏时自动从备份恢复

> ⚠️ 从旧版本升级:如果之前部署过标 `\Answered` 的版本,那些标记不会自动清除,但新版本不再读取它们,不影响使用。想清理可以在客户端取消这些邮件的"已回复"标记。

### 2.7 邮件我在手机上读过了,还能收到飞书通知吗?

**能。** 这是本项目的核心设计。

早期版本用 `SEARCH UNSEEN` 找待处理邮件,等于把 `\Seen` 标记当成了"处理过没有"。但 `\Seen` 是**用户行为**:你在手机上点开看一眼,标记立刻变成已读,下一轮搜索直接搜不到它,推送就永久丢了。**"用户读没读"和"我们推没推过"是两件完全不同的事,不能共用一个标记。**

现在的做法是用**本地 UID 水位线**记录状态,搜索条件不再看 `\Seen`:

| 方式 | 状态存哪 | 读信会干扰吗 | 重启/换机器会丢吗 |
|---|---|---|---|
| `\Seen`(旧) | 服务器 | ❌ 会,一读就置位 | 不会,但语义全错 |
| **`watermark`(默认)** | 本地 `data/` | ✅ 不会 | ⚠️ 会,文件丢了就退化成全量重扫 |

关键点:

- **推送成功**后才推进水位线。被过滤/屏蔽的邮件不推进,下次还会被判定一次
- 水位线只记录"处理到哪个 UID",**跟邮件本身没有任何关系** —— 不写 `\Seen`、不写 `\Answered`、不加关键字
- 记录位置在 UID 上,所以**不管邮件被读过还是没读过,只要 UID 更大就会被处理**

**确实会漏的极端情况:**

- **邮件被读过之后又被删除 / 移动到别的文件夹** → 拉不到了。只能靠调小 `POLL_INTERVAL` 缩短窗口,或者改成 IMAP `IDLE` 实时监听
- **`data` 卷丢失或状态文件损坏** → 冷启动,跳过历史。这就是为什么不碰邮件是有代价的,务必挂好 `./data`(脚本会自动保留 `.bak` 备份降低风险)
- **首次部署时时间窗内已有历史邮件** → 会先建立基线(记录当前最大 UID,不补推),避免一次性刷屏。基线之后再到的邮件正常推

### 2.8 容器重启很频繁,重启后会漏邮件吗?

**不会,只要 `./data` 挂载正常。**

状态存在本地 `data/uid_state.json`,重启只是读回水位线继续增量。只需分清两个概念:

| | 含义 | 会不会漏信 |
|---|---|---|
| **重启** | 进程重启,读回 `data/uid_state.json` 的水位线 | 不会,接着上次的 UID 继续增量 |
| **冷启动** | 水位线文件不存在 / 读不出来 / `UIDVALIDITY` 变化 | 会跳过历史(不补推),之后的新邮件不受影响 |

**启动日志会明确告诉你走的是哪条路:**

```
📂 状态文件: /data/uid_state.json
💾 已恢复 1 个邮箱文件夹的水位线 —— 重启后继续增量拉取
[xxx@163.com] 📌 状态记录方式: 本地 UID 水位线(完全不碰邮件: 不改已读、不改已回复、不加关键字)
```

- `💾 已恢复 N 个邮箱文件夹的水位线` → 走增量,重启不影响
- `🆕 状态文件不存在` → volume 没挂上或首次运行,会建立基线(不补推历史)
- `(用备份恢复)` → 主文件损坏,已自动从 `.bak` 恢复
- `📌 状态记录方式: ...` → 告诉你实际用的是哪种方式

**顺手把重启本身也优化了:** 旧部署方式每次容器启动都要 `pip install requests`,联网拉包几十秒起步,PyPI 抖动时直接失败,配合 `restart: always` 就是无限重启循环——而这段时间邮件是没人管的。现在依赖预装进 `Dockerfile` 的镜像层,**重启是秒级的,且完全不需要外网**。

> 升级提示:从旧版本升级需要执行一次 `docker compose up -d --build`,之后改配置用 `docker compose restart` 即可(代码是单独挂载的,不用 rebuild)。

### 2.9 状态文件是什么?要手动创建吗?

**不用手动创建。** 脚本第一次跑起来会自己生成,你什么都不用做。

它长这样(就这么多内容):

```json
{
  "your_email@163.com|INBOX": {
    "uidvalidity": "1234567890",
    "last_uid": 149000
  }
}
```

`last_uid` 就是"已经处理到这个 UID 了"。每轮是**覆盖写**这个数字,不追加,所以跑十年也不会变大。

**文件在哪:**

| 环境 | 路径 | 说明 |
|---|---|---|
| 容器内 | `/data/uid_state.json` | `UID_STATE_FILE` 决定 |
| 宿主机 | `./data/uid_state.json` | 由 `docker-compose.yml` 的 `./data:/data` 映射出来 |

宿主机上的 `data/` 目录**不用手动建**,`docker compose up` 时 Docker 会自动创建。

**目录里会有三个文件:**

| 文件 | 作用 | 可以删吗 |
|---|---|---|
| `uid_state.json` | 主状态记录 | 删了会重建基线,跳过历史邮件 |
| `uid_state.json.bak` | 上一版备份 | 可以,主文件没问题时用不上 |
| `uid_state.json.tmp` | 写入过程中的临时文件 | 可以。正常情况下会立刻被重命名掉,如果残留说明进程写过一半被杀 |

**怎么确认它在正常工作:**

```bash
# 宿主机上
ls -lh data/
cat data/uid_state.json
```

首次启动时日志会出现:

```
💾 已创建状态文件: /data/uid_state.json
```

之后每次重启是:

```
💾 已恢复 1 个邮箱文件夹的水位线 —— 重启后继续增量拉取
```

如果看到 `⚠️ 状态文件目录不可写`,说明 `./data` 挂载有问题,权限或路径不对,这时每次重启都会丢进度。

**想手动重置(从当前最新邮件重新开始):**

```bash
docker compose stop
rm -f data/uid_state.json data/uid_state.json.bak
docker compose start
```

脚本会重建基线,把当前邮箱里的最新 UID 记为起点,不从历史补推。

**想放到别的位置:** 改 `UID_STATE_FILE` 即可,比如挂到 NAS:

```yaml
volumes:
  - /mnt/nas/lark-mail:/data
```

**迁移到另一台机器:** 把 `data/` 整个目录拷过去就行,水位线会接着用。前提是目标邮箱的 `UIDVALIDITY` 没变(换了服务器或邮箱被重建的话,脚本会自动识别并重建基线)。

### 3. 脚本会改动邮件状态吗?

**默认不会。一个字节都不改,连 `STORE` 命令都不发。**

脚本对邮箱只用这三种命令,全部是只读的:

| IMAP 命令 | 干什么 | 会改状态吗 |
|---|---|---|
| `SELECT` / `SEARCH` | 选文件夹、搜 UID | 不会 |
| `FETCH (BODY.PEEK[])` | 拉邮件正文 | 不会(`PEEK` 正是为了避免像 `BODY[]` 那样隐式标已读) |

没有 `STORE` 意味着:**不标已读、不标已回复、不加关键字、不标星、不移动、不删除**。邮件在服务器上的状态和没装这个脚本时完全一致。

只有下面这些**显式配置**才会让脚本改动邮件:

| 配置 | 会改什么 | 什么时候才需要 |
|---|---|---|
| `MARK_SEEN=true` | 标 `\Seen`(已读) | 单人独用、想在客户端区分"推过的" |
| `PUSH_MODE=keyword` | 加 `$LarkMailPushed` | 想让状态存服务器而不是本地 |
| `PUSH_MODE=answered` | 标 `\Answered`(已回复) | ❌ **共用邮箱绝对不要用** |

默认值(`PUSH_MODE=watermark` + `MARK_SEEN=false`)下,上面三条一个都不命中。

各场景明细:

- 被时间过滤 / 屏蔽词跳过的邮件 → **什么都不写**,只是本地记一笔不重复处理
- 推送失败(卡片和纯文本都失败)的邮件 → 什么都不写,下次轮询自动重试
- 推送失败超过 `MAX_RETRIES` 次(默认 3) → 只在本地推进水位线放弃,邮件本身不动
- 同一轮**连续多封** fetch 失败 → 视为连接异常,自动重连并退避,不再逐个空跑


### 4. 历史邮件刷屏

脚本默认跳过 24 小时前的邮件。如果积压了大量未读邮件,可调小 `BLOCK_BEFORE`(如 `3600` = 只推最近 1 小时),并调小 `MAX_EMAILS_PER_RUN` 控制单次推送量。

### 4.5 跑几个月会不会把磁盘吃满?

**不会。状态文件大小是恒定的,不随邮件数量增长。**

水位线只记"处理到哪个 UID",每轮是**覆盖写**,不是追加。实测连续处理 50000 封邮件(约等于每天 200 封跑 8 个月)后:

```
uid_state.json     96 字节
uid_state.json.bak 96 字节
```

一年下来也就是两个几十字节的 JSON,加起来的体积还不够一张缩略图。

其他可能的占用:

| 项目 | 增长情况 | 上限 |
|---|---|---|
| `data/uid_state.json` | **恒定**,只记 UID 指针 | ~100 字节/账户 |
| `data/uid_state.json.bak` | 同上,覆盖写 | ~100 字节/账户 |
| 进程内存(去重记录) | 只保留 **7 天**内的 Message-ID,每轮自动清理 | 几千条 ≈ 几 MB |
| 进程内存(屏蔽记忆) | 时间窗内清理 + 10 万条硬上限 | ≈ 13 MB |
| Docker 日志 | 已配置轮转 | **30 MB**(10m × 3 个文件) |
| 镜像 | 每次 `--build` 会留旧层 | 手动 `docker image prune -f` |

想自己确认的话:

```bash
du -sh data/                 # 状态文件占多少
docker system df             # 镜像 / 容器 / 卷 各占多少
docker logs lark-mail 2>&1 | wc -c   # 当前日志体积
```

### 5. 其他邮箱(QQ / Gmail / 企业邮箱)

**最容易踩的坑**: 用的是企业邮箱(如 `me@company.com`),却忘了改 `IMAP_SERVER`,还留着默认的 `imap.163.com`。结果服务器回一句 `LOGIN Login error or password error`,看着像密码错,其实是它根本不认识这个账号。

常见服务商对照:

| 邮箱 | IMAP_SERVER | 端口 | 密码用什么 |
|---|---|---|---|
| 163 / 126 | `imap.163.com` / `imap.126.com` | 993 | **授权码**,不是登录密码 |
| QQ / Foxmail | `imap.qq.com` | 993 | **授权码** |
| Gmail | `imap.gmail.com` | 993 | 应用专用密码(需开两步验证) |
| Outlook / Hotmail | `outlook.office365.com` | 993 | 账户密码或应用密码 |
| 腾讯企业邮 | `imap.exmail.qq.com` | 993 | 客户端专用密码 |
| 阿里企业邮 | `imap.qiye.aliyun.com` | 993 | 登录密码 |
| 网易企业邮 | **`imap.qiye.163.com`** | 993 | 登录密码或客户端授权码 |

> ⚠️ 网易企业邮千万别填成 `imap.163.com` —— 那是**个人邮箱**服务器,不认企业账号,只会回一句 `LOGIN Login error or password error`。华东节点也可以直接用 `imaphz.qiye.163.com`。

**不确定自己公司用的哪家?** 查 MX 记录最准:

```bash
dig +short MX your-company.com
nslookup -type=MX your-company.com   # 没装 dig 的话用这个
```

- 出现 `mxbiz1.qq.com` / `mxbiz2.qq.com` → 腾讯企业邮
- 出现 `mx1.qiye.aliyun.com` → 阿里企业邮
- 出现 `mx.zoho.com` → Zoho Mail
- 出现 `outlook.office365.com` → 微软 365
- 都不是 → 自建或小众服务商,直接问 IT 要 IMAP 地址和端口

> 脚本已经内置了这个检查:登录失败且发现「邮箱域名」和「IMAP_SERVER」明显对不上时,会直接把怀疑方向打在日志里,省得你对着"密码错误"反复试授权码。

多账户模式下,每个账户可配置不同的 `imap_server` / `imap_port`(在 JSON 中加上这两个字段即可)。

### 6. 多账户 JSON 解析报错(`解析 MAIL_ACCOUNTS_JSON 失败`)

- 确认 `MAIL_ACCOUNTS_JSON` 是**一整行**,中间没有任何换行
- 每个账户用 `{ }` 包裹,账户之间用 `,` 分隔,整体是 `[ ]` 数组
- 键名和值都用**双引号**,检查是否漏了引号或括号
- 可在本地先验证 JSON 合法性:`python -c "import json,sys; json.loads(sys.argv[1])" '你的JSON'`,无输出即合法
